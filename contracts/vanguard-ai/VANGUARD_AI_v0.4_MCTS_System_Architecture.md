# VANGUARD AI v0.4 — MCTS System-Wide Architecture Contract

**Status:** PROPOSED / EXPERIMENTAL ARCHITECTURE
**Version:** 0.4
**Parent:** VANGUARD AI v0.3 Harness Adapter Contract
**Change Type:** ADD
**Scope:** System-wide MCTS control/selection layer

## 1. Purpose

This update does not replace the v0.3 Harness Adapter. It introduces a
system-wide architectural rule for tracing MCTS through VANGUARD without
making every subsystem an MCTS implementation.

MCTS is treated as a decision/search mechanism that can sit above replaceable
capabilities. It selects among actions, capabilities, agents, tools, or
research branches according to state, value, uncertainty, cost, and
verification evidence.

## 2. System Position

```text
                    VANGUARD
                        |
                 Goal / State Model
                        |
                  MCTS Decision Layer
                        |
              +---------+---------+
              |                   |
        Capability Choice     Research Choice
              |                   |
          ORCHESTRATO       Knowledge/Internalization
              |
          Policy Gate
              |
       Harness / Provider
              |
             Tool
              |
       Observation / Evidence
              |
        Verification
              |
          Reward / Value
              |
        MCTS Tree Update
              |
          Next Decision
```

MCTS does not own security, permissions, architectural authority, or durable
knowledge. Those remain outside the search algorithm.

## 3. Tree Semantics

A node represents a decision state, not merely a text fragment.

Minimum conceptual state:

- system state
- task/objective
- available capabilities
- permission context
- candidate action
- observation
- reward/value
- verification evidence
- cost/risk
- parent/children
- visit statistics
- provenance/trace identifier

A branch therefore represents an executable hypothesis:

`state -> action -> observation -> evaluation -> next state`

## 4. Existing MCTS Assets

The library already contains tree-first MCTS/T5 implementations in which
the Experience Tree is the primary runtime structure, candidate actions are
generated by a model capability, and trajectories become learning
experience. These remain experimental components rather than a mandate that
all VANGUARD execution use T5.

The existing verMCTS concept in VERITAS-AIXI remains the verification-aware
decision/search component.

## 5. MCTS Across the Architecture

MCTS may operate at several scales while sharing one conceptual contract:

### Level A — Task Planning
Select the next task/action branch.

### Level B — Capability Selection
Choose among Browser, Lean, RAG, Code, Compute, Harness, etc.

### Level C — Agent/Runtime Selection
Choose an available agent/runtime according to expected value, cost, risk,
latency, and evidence.

### Level D — Tool Sequence
Search over multi-step tool trajectories.

### Level E — Research
Explore hypotheses, experiments, reproductions, and verification routes.

### Level F — Evolution
Explore candidate code changes, tests, benchmarks, and rollback paths.

These are search domains, not separate MCTS engines by default.

## 6. Reward / Value Boundary

The reward function is domain-specific and replaceable.

A generic system-level value may combine:

`expected_benefit - cost - risk + verification_gain + capability_gain`

but no fixed numeric weighting is mandated by this contract.

For high-stakes actions, policy/verification gates dominate model-estimated
value. MCTS cannot turn an unauthorized action into an authorized one.

## 7. LoRA Relationship

LoRA is not itself a search controller.

Where LoRA adapters exist, an MCTS node may reference an adapter state as part
of the candidate configuration:

`Node -> Model/LoRA configuration -> Action -> Observation -> Evaluation`

This preserves the earlier concept of LoRA as a composable learning/modulation
unit rather than making LoRA the global architecture.

MCTS may decide when an adapter is useful, but the adapter does not gain
architectural authority.

## 8. Harness Relationship

The Harness Adapter is an execution leaf/branch provider.

The preferred loop is:

`MCTS -> abstract capability/action -> Policy -> Harness Adapter -> runtime
-> observation -> verification -> value update`

Harness internals must not leak into tree-state semantics beyond normalized
observations, outcomes, costs, and evidence.

## 9. Knowledge Internalization

MCTS-generated experience is not automatically trusted knowledge.

`Search trajectory -> evidence -> reconstruction/reproduction -> verification
-> evaluation -> internalization candidate -> Knowledge Store`

This preserves the v0.2 trust lifecycle.

## 10. State Separation

MCTS tree state belongs to Runtime State while a search episode is active.

Promoted knowledge belongs to Knowledge State only after the existing trust
and verification lifecycle.

Architectural changes belong to Master State only after Change Request
reconciliation and approval.

No MCTS operation may silently cross these state boundaries.

## 11. Failure and Recovery

A failed branch becomes evidence.

The system should preserve:

- failure class
- action/capability
- observed context
- verification result
- rollback result
- reusable failure fingerprint where available

A recovery search may then explore alternative branches rather than blindly
repeating the failed action.

This provides a natural interface to the existing damage-resilient nucleus,
without coupling the nucleus to one MCTS implementation.

## 12. Multi-Agent Interpretation

Agents are candidate actions/providers in the search space.

MCTS may select:

`Agent A -> Tool -> Verify`

or

`Agent A -> Agent B -> Verify`

or

`Agent A -> Harness -> Agent B -> Verify`

but multi-agent execution remains optional and policy-controlled.

## 13. Implementation Boundary

The minimum implementation should expose:

1. `SearchState`
2. `ActionCandidate`
3. `TreeNode`
4. `SearchResult`
5. `ValueEvaluator`
6. `VerificationResult`
7. `MCTSController`
8. adapters for Capability/Policy/Execution
9. trace/audit integration

Do not duplicate ORCHESTRATO registries or policy services.

## 14. Acceptance Criteria

The architecture is accepted experimentally when:

- MCTS can select an abstract capability without knowing its implementation.
- Policy can deny a selected branch.
- Harness execution returns normalized observations.
- Verification can update branch value.
- Failed branches remain traceable.
- Runtime state does not overwrite Knowledge/Master state.
- A model or LoRA adapter can be swapped without changing tree semantics.
- The same search contract can be reused for task, research, and evolution
  experiments.

## 15. Non-Goals

- MCTS is not declared the sole global controller.
- MCTS does not replace ORCHESTRATO.
- MCTS does not replace policy/security.
- LoRA does not become the decision engine.
- DeepSeek Harness does not become a core dependency.
- No AGI claim is made.
